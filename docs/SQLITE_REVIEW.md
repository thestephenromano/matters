# SQLite verification review

Follow-up to PR #101 (`a5a6060eaa0a63fa4247cf2af1db723f63c8afcf`), implemented on main after #102. The active execution record binds the corrected files and records regression/mutation output. This remains verification of integration and upstream provenance, not a local reproduction of the WAL-reset race.

## Findings and owning boundaries

1. **Unfrozen baseline graph:** its ignored lockfile and CI command without `--locked` allowed registry changes to change the linked runtime. A locally generated lockfile used by a focused `--locked` probe did not freeze CI. Commit the baseline's own lockfile and require `--locked` in CI/measurement commands. A missing-lock witness confirms Cargo refuses to create it. The prototype remains a separate Cargo graph.
2. **Uncached baseline build:** direct manifest invocation selected `baseline/target`, outside the configured cache workspace. CI now selects `target/baseline` (under any local build-root override) and explicitly configures that workspace in rust-cache.
3. **Lost intermediate commits:** overwriting all rows erased earlier observations. The fixture appends each generation under a distinct primary key and validates every row/payload. Deleting generation 1 after all commits is a targeted failure witness.
4. **Ineffective checkpoints:** busy or negative frame counts cannot establish progress. Channel coordination now holds a writer transaction open while PASSIVE copies committed frames, requires positive observed progress, and requires eight completions for each of the four modes. A racing attempt may encounter contention, but completion after the commit is still required. This does not claim control of SQLite's internal instruction interleaving.
5. **Unenforced file-backed journal mode:** the app schema and replica initializer discarded the PRAGMA result. Persistent open now checks `wal` before schema initialization. New regressions fail on the old code because SQLite legitimately returns `memory` for `:memory:`. Actual file open/reopen tests check WAL, and explicit in-memory app/replica APIs remain supported. Sibling search found the encrypted outbox already enforces DELETE.
6. **Crash before dirty-page spill:** the old fixture could fit entirely in cache. The worker now has a four-page cache and eight four-page payloads; the parent verifies real WAL frames before recovery. Before-commit frames have no commit marker, while after-commit frames have one. Recovery and backup verify committed generations only. Disabling spill is a targeted failing mutation.
7. **Inactive app evidence:** the app/baseline inventory was explicitly revision-bound, but did not gate current app inputs; `ci/check.sh` had already changed after #101. Promote current app/baseline files and lockfiles into the active required source hashes. The guard tests altered/deleted files and omitted required hashes, including the baseline gate and lockfile. Old inventory is retained only as historical evidence. *Superseded 2026-11-18:* the prototype workflow runs on every PR, so gating app-owned and project-wide CI inputs blocked unrelated app changes. Active bindings are now limited to prototype-owned paths, the baseline runtime probe runs in prototype CI, and the app inputs are kept as provenance in `historical_app_source_sha256`. The app's own CI enforces the runtime identity and journal mode against current source.
8. **Ambiguous upgrade reference:** #97 remains a valid completed issue reference, rather than a new outstanding dependency. Replace `wal_upgrade_issue` with an explicit completed upgrade record linking #97 and merged #101.
9. **Repeated runtime query:** all three probes now invoke one connection-based helper. The baseline declares the existing pinned rusqlite as a test dependency, unified with its app dependency and covered by its own lockfile.
10. **Default-feature rationale:** disabling defaults did not benefit the native build; the WebAssembly backend is target-conditional. Restore defaults, retain the bundled feature, and record the target-specific lockfile additions without claiming a native backend change.

## Assurance scope

The owning guards, durable-history assertions and evidence checks are exercised by baseline failures, focused tests and named mutations. Final full app/prototype gates run after restoring all mutated source. See the active evidence for exact commands, outputs and counts. No new storage/crypto library, schema migration, performance claim or cross-target durability claim is introduced. Callers using a memory path must use the explicit in-memory API instead; persistent app/replica APIs require a WAL-capable file.
