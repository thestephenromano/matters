# Durable authenticated receive experiment

Status: bounded integration-test support for [#35](https://github.com/thestephenromano/matters/issues/35) and [#36](https://github.com/thestephenromano/matters/issues/36). Neither issue is closed. No application database, network service or user key store uses this code.

## Adopted components and boundary

Extend the approved SQLite/rusqlite, Loro, minicbor and HPKE/ML-DSA dependencies. Adopt the transactional-inbox pattern: retain input and receipt progress together, then atomically publish application results. [SQLite transactions](https://www.sqlite.org/lang_transaction.html) own commit/rollback and single-writer serialization. [Loro persistence](https://loro.dev/docs/tutorial/persistence) requires pending input to survive independently of a normal snapshot. This experiment retains original encrypted input instead of using snapshots as a receipt ledger. A separate message broker or database engine provides no needed capability for this local transaction boundary. No new library, primitive, transport or storage service is selected.

The implementation is [encrypted_inbox.rs](../experiments/sync-prototype/tests/support/encrypted_inbox.rs), with [executable cases](../experiments/sync-prototype/tests/cases/encrypted_inbox.rs). It reuses the signature/context/epoch gate from [key distribution](SYNC_KEY_DISTRIBUTION.md), the full-record SHA-384 chain definition and the existing task projection. `Authority::authenticate_data` produces a read-only authenticated record handle; only that handle can decrypt. The earlier first-record helper retains its stricter null-predecessor and first-actor-range checks.

## Identity and trust

The caller supplies an independently trusted application/tenant/collection/document route, pinned root, signed genesis, ordered signed writer starts and a local receive-stream generation. Bootstrap and writer admission validate that bundle before opening storage. The exact bundle is bound to the database and cannot change on reopen. Membership and writer forks in configuration fail opening. Configuration admits only root writer starts: a replacement start would retire its predecessor's valid history, so it fails opening too. Changes, retired writers, unknown writers, epochs and snapshots require later lifecycle work.

The approved [account model in #34](https://github.com/thestephenromano/matters/issues/34) uses a random application-scoped tenant identifier without a user name, email address or profile. Identifiers do not grant access. Login/billing identity mapping stays outside the sync data plane; encrypted record validation uses independently trusted opaque IDs. This experiment has no login, billing, token or telemetry integration and cannot establish their privacy properties. Route IDs, device relationships, sizes, timing and network metadata are not anonymity guarantees.

One collection/document and one fixed membership epoch are supported per database. Keys are caller-supplied authenticated `EpochKey` handles and remain in memory. Their route/manifest/epoch must match before processing starts. The signed epoch message commits to its content key and an `EpochKey` handle can only hold that committed key ([key distribution](SYNC_KEY_DISTRIBUTION.md#epoch-content-key-commitment)), so a failed authenticated decryption of a signed record is a verdict on the record: it is quarantined as `authenticated-decryption`. No key persistence or recovery ceremony is implemented.

## Transactions and observable states

| Boundary | Committed together | Retry/restart behavior |
| --- | --- | --- |
| Receipt | Exact input bytes, local stream position and `waiting/unprocessed` status | Retrying the same position and bytes is a no-op; different bytes at that position fail. |
| Application | Accepted replay order, quarantine/wait/fork classifications and complete task projection | Reconstruct accepted engine state from encrypted records in committed application order, then retry pending records. |

Receipt positions start at one and are contiguous within the caller-pinned generation. Missing positions, changed generations and oversized inputs fail without advancing progress. This is a bounded local stream contract, not a selected relay pagination API. In-range malformed records are retained before processing; receipt progress means bytes are recoverable, not that their contents were accepted. There is no network acknowledgement or durability promise to a remote peer.

Both transactions use `BEGIN IMMEDIATE`. Persistent opens require SQLite to return WAL mode and set `synchronous=FULL`; `:memory:` is rejected. A dedicated format marker and exact configuration binding reject other databases. Any user schema object (table, index, view or trigger, including names such as `SQLiteCache`) requires that marker; the check is shared with the outbox and `Replica`. Validation is repeated under the initialization transaction to protect competing openers. Busy/SQL errors roll back and can be retried. Capacity does not depend on opens or failed attempts.

Authoritative accepted state is the retained ciphertext, its application order, and an engine snapshot committed in the same transaction as that order and the projection. Authentication facts (record ID, incarnation, predecessor, digest, actor) depend only on retained bytes and the bound configuration; they are derived once and committed with the row. The receiver has no long-lived in-memory document to get ahead of a failed commit. Processing loads the committed snapshot and stages each candidate in a fork of it. Projection, snapshot and order updates cannot commit separately. No incoming path writes an outgoing queue. The stored projection contains plaintext and the database/WAL/backups are not encrypted at rest.

`entries()` exposes original bytes, sequence, classification, a payload-free reason, optional committed application ordinal and whether another writer signed a different record under the same record ID. `projection()` returns the committed view of all accepted records. States that only concurrency produces are repaired deterministically in the projection and listed in its `repairs`: entities created concurrently under one UUID become an original and conflict copies, and duplicate or non-task Today references are skipped ([ADR 0001](decisions/0001-crdt-adoption.md) C18–C19). If a merged state still failed projection, `projection()` would return an error and `merge_conflict()` would report `domain-merge-conflict`, identically on every receiver holding the same input; a seeded property test over merged concurrent histories asserts this never happens for valid commands. Callers must inspect classifications as well as the view: an observed fork can freeze a chain after earlier records were accepted. This experiment preserves that prior view and its history; it does not silently roll back or choose a fork winner.

## Admission and conflicts

1. Validate canonical content encoding and independently expected route, current membership/epoch, admitted active writer and original-byte ML-DSA signature. Unsupported or unauthenticated inputs are quarantined without contributing chain claims.
2. Detect exact-byte duplicates by full-record digest. A duplicate names its first retained copy (`duplicate-of:<sequence>`), whose classification governs, and is never applied again.
3. Gather signed record identities and `(incarnation, predecessor)` claims across retained records before decrypting or importing. Two different authenticated successors, including two null roots, freeze that incarnation. One incarnation signing two different records under one record ID is equivocation and freezes that incarnation. When different incarnations sign records under one record ID, either writer or the relay may be at fault, so neither chain is frozen; both rows are flagged as record-ID conflict evidence and judged on their own chains. Each record's content key is derived from its full header, so the collision never reuses a key. Retain all byte strings.
4. Decrypt through the authenticated handle. A valid competing signature remains fork evidence even if its AEAD or CRDT payload is invalid. A forged competitor cannot freeze a chain.
5. Require the predecessor to equal the accepted head for that incarnation. Keep unresolved records waiting. A descendant of a retained quarantined/forked predecessor reports `blocked-by-rejected-predecessor`; deeper unresolved dependencies remain visible as waiting.
6. Admit only Loro Updates blobs with a positive range for the writer's single admitted actor. Reject overlapping ranges and snapshot blobs. Wait for missing actor counters or declared dependencies before copying engine state, and for causal dependencies found on import. After staged import, require no pending engine updates and exactly the expected full version vector. Then judge domain validity in the record's own causal past: the engine state at the record's last operation, containing only what that record depends on. That state must project, it may not need a merge repair that the same past without the record's operations did not (`domain-repair`), since only concurrency may produce a conflict copy, and it may not remove a tombstone (`deletion-evidence`). `matters_sync_prototype::causal_past_verdict` implements this once for the inbox and `Replica`. A verdict therefore never depends on delivery order or on concurrently applied records, and a payload rejection is final.
7. Repeat the pending pass until no additional record can apply. Persist classifications, snapshot and projection atomically. Application order can differ from delivery order.

Fork evidence is recomputed on each pass from the committed authentication facts of all retained signed input. Rejected inputs can be inspected after restart; processing does not silently discard them. Local arbitrary database tampering, rollback by a hostile local operator and cryptographic hash collisions are outside this experiment's model.

## Budgets and evidence scope

Choose at most 32 retained deliveries per database and the existing content-record wire cap per delivery (roughly 32 MiB of input at the limit). This is an inspectable fixture budget, not a service quota. Duplicate deliveries at new positions also consume it; an exact retry at an existing position does not. At capacity, reopen, inspection, processing and existing-position retries remain available. There is no pruning.

Settled history costs no signature checks, decryption or staging on later passes. Each new row is authenticated once for its facts and once more when it is opened. Each eligible candidate is staged in one engine fork plus two causal-past forks (with and without the record). Tests pin these counts. Candidate plaintext, engine staging, the snapshot and SQLite pages require additional space. Neither the input cap nor the fixture count establishes a decompression/CPU/memory bound for hostile signed Loro updates. No latency or production throughput claim follows.

Tests cover reversed delivery, missing cross-writer causality, duplicate positions/records including A/B/A delivery, rejected predecessors, forks before/after prior application, forged competitors, same-writer record-ID equivocation, cross-writer record-ID reuse in both delivery orders, concurrent creations under one UUID converging to an original and a conflict copy in both delivery orders, a record introducing a merge repair in its own causal past, records sealed under a key other than the committed epoch key, settled-history work budgets, replacement writer starts, view-only foreign databases, signed undecryptable branches, actor overlap, malformed domain state, cross-tenant/unsupported snapshot inputs, wrong-context key handles, two database handles, real SQLite write contention, SQL trigger rejection, capacity, foreign storage and restart. Four child-process exits cover before/after receipt and application commits. Direct discovery of the ignored helper is a no-op only when all worker variables are absent.

The [active evidence](../experiments/sync-prototype/evidence/record-contract-2026-11-18.json) records commands, source hashes and deliberate guard-removal results. CI checks those bindings, independent fixtures, formatting, Clippy and both normal and ignored-inclusive suites. Process exits on the recorded local filesystem do not establish power-loss, media-failure or host-loss durability.

## Remaining gates

Collection-wide record-ID conflict indexing before supporting multiple documents; merge policies for invariants added after the current command set, each proven against the seeded merge property test; durable changing membership/writer authority, enrollment and revocation/rotation, historical closing frontiers, snapshots/checkpoints and safe pruning; full hostile-document/schema/resource admission; persistent key storage and recovery; atomic integration with local domain commands/outbox; a service API with restore generations and remote durability semantics; production retention and disk exhaustion handling; exact-suite independent interoperability, cross-target runs and independent security review. Fixed configuration is not transparent account recovery or support for old retained outbox writers.
